## 1. Operating Models & Environment Parity

The system operates under two distinct environments designed with 100% functional parity:

```
┌──────────────────────────────────────┐     ┌──────────────────────────────────────┐
│       1. Local Development           │     │       2. AWS Zero-Cost Production    │
├──────────────────────────────────────┤     ├──────────────────────────────────────┤
│ • Next.js Dev Server (Port 3000)     │     │ • S3 Static SPA + CloudFront CDN     │
│ • FastAPI Monolith (Port 8000)       │     │ • AWS Lambda Modular Monolith        │
│ • Local PostgreSQL Container         │     │ • AWS RDS db.t4g.micro (Private VPC) │
│ • Direct Same-Machine API Calls      │     │ • Same-Origin CloudFront Proxy (/api)│
└──────────────────────────────────────┘     └──────────────────────────────────────┘
```

### 1.1 Local Development Quickstart & Daily Operations

The local development environment uses a streamlined 2-container Docker Compose setup (`motoshop-db` and `motoshop-backend`) with direct local hot-reloading for rapid developer feedback:

#### 1. Start Database & Backend Services
```bash
# Start PostgreSQL (port 5432) and FastAPI Modular Monolith (port 8000)
docker compose up -d

# Verify container health and logs
docker compose ps
docker compose logs -f backend
```

#### 2. Start Frontend Development Server
```bash
cd frontend
npm install
npm run dev
```
The Next.js client boots at `http://localhost:3000` with hot-module replacement and dynamic routing enabled. The client directly queries the FastAPI backend at `http://localhost:8000/api/v1`.

#### 3. Interactive Documentation & Health Endpoints
- **Interactive Swagger UI**: `http://localhost:8000/docs`
- **ReDoc API Documentation**: `http://localhost:8000/redoc`
- **Service Health Check**: `http://localhost:8000/health`
- **OpenAPI Schema Definition**: `http://localhost:8000/openapi.json`

#### 4. Stopping and Resetting Local Environment
```bash
# Stop containers without losing database volume
docker compose down

# Full reset including database volume recreation (fresh state)
docker compose down -v
docker compose up -d --build
```

## 3. Database Migration Runbook (Zero-Cost Private VPC Execution)

### 3.1 The NAT Gateway Dilemma & Zero-Cost Solution
* **Problem**: In AWS, a private RDS instance cannot be reached from GitHub Actions without provisioning an AWS NAT Gateway ($32.40/month) or Bastion Host EC2 ($10/month), violating the zero-cost mandate.
* **Solution**: Migrations are bundled into the Lambda container and executed by the internal `MigrationFunction` (`app.migrations.runner.handler`). Because Lambda functions reside directly inside the private database VPC subnet (via Hyperplane ENI), migrations run locally at **$0.00 cost**.

### 3.2 Automated Migration Trigger (CI/CD Pipeline)
During backend deployment, GitHub Actions triggers the VPC migration function via the AWS CLI:
```bash
aws lambda invoke \
  --function-name motoshop-db-migration \
  --payload '{}' \
  --cli-binary-format raw-in-base64-out \
  migration_output.json

cat migration_output.json
```

### 3.3 Manual On-Demand Migration Trigger
If the administrator needs to force schema updates manually from a local terminal:
```bash
aws lambda invoke \
  --region ap-southeast-1 \
  --function-name motoshop-db-migration \
  --payload '{}' \
  response.json
```

## 4. Maintenance & Storage Retention (RDS Free Tier Limits)

### 4.1 RDS Free Tier Boundaries
- **Compute**: 750 hours/month of `db.t4g.micro` (1 continuously active instance consumes 744 hours in a 31-day month).
- **Storage**: 20 GB of gp3 SSD storage.
- **Automated Backups**: 1-day retention is included for free.

### 4.2 Storage Capacity Management
With 5 shop users creating ~100 transactions/day, database growth is estimated at ~15 MB/month. 
20 GB storage provides **over 10 years of headroom**.
- **Audit Log Retention Policy**:
  Audit logs (`audit.logs`) older than 2 years may be dumped via a scheduled script to cold S3 storage (S3 Glacier Flexible Retrieval at $0.0036/GB/month) to maintain RDS storage well below the 20GB threshold.

## 5. Disaster Recovery & Rollback Protocols

### 5.1 Frontend Rollback (RTO < 2 minutes)
If a bad frontend build is released:
1. Re-deploy the previous commit via GitHub Actions, or manually re-sync the previous static artifacts:
   ```bash
   aws s3 sync previous_build/ s3://$S3_BUCKET_NAME --delete
   ```
2. Invalidate the CloudFront edge cache:
   ```bash
   aws cloudfront create-invalidation \
     --distribution-id $CLOUDFRONT_DISTRIBUTION_ID \
     --paths "/*"
   ```

### 5.2 Backend Monolith Rollback (RTO < 5 minutes)
If an API bug is deployed to AWS Lambda:
1. Roll back the CloudFormation SAM stack using AWS SAM CLI:
   ```bash
   sam rollback --stack-name motoshop-pos-prod
   ```
2. Or point the Lambda `$LATEST` alias back to the previous stable container image tag via the AWS Lambda Console / CLI.

### 5.3 Database Disaster Recovery (Point-in-Time Restore)
If data corruption occurs:
1. RDS automatically creates continuous transaction logs.
2. Restore the database to any point within the last 24 hours:
   ```bash
   aws rds restore-db-instance-to-point-in-time \
     --source-db-instance-identifier motoshop-rds \
     --target-db-instance-identifier motoshop-rds-restored \
     --restore-time 2026-09-25T08:00:00.000Z
   ```
3. Update the `DatabaseUrl` parameter in CloudFormation to point to the restored instance.
